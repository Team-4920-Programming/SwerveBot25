VISION-BASED POSE ESTIMATION CONFIDENCE CALCULATOR REWORK
Team 4920 - FRC Robot
Date: 2025-12-23

================================================================================
PROBLEM STATEMENT
================================================================================

The original confidence calculator was discarding valid AprilTag detections,
causing the robot to lose odometry and overshoot target poses. Analysis revealed
multiple algorithmic issues that penalized good measurements and rewarded bad
strategy choices.

Key symptoms:
- Tags were being rejected despite good visibility and measurement quality
- Robot losing position tracking in mid-routine
- Overshooting targets by large margins due to sparse vision updates
- Multiple visible tags were actually reducing confidence instead of improving it


================================================================================
ROOT CAUSE ANALYSIS
================================================================================

Original Formula Issues (lines 160-187 in old code):

1. INVERTED DISTANCE LOGIC
   Problem: max(0, smallestDistance - 2.5) * 7
   - Tags at 1-2 meters away: penalty = max(0, -1.5) = 0 (GOOD measurement treated as neutral)
   - Tags at 4 meters away: penalty = 1.5 * 7 = 10.5x worse confidence
   - This penalized close, high-quality measurements and over-penalized distant ones

2. MULTIPLE TAGS PENALIZING CONFIDENCE
   Problem: divisor = 1 + ((numTags - 1) * 10)
   - 1 tag: divisor = 1.0 (baseline)
   - 2 tags: divisor = 11.0 (11x WORSE confidence!)
   - 3 tags: divisor = 21.0 (21x WORSE confidence!)
   - This is backwards. Multiple tags should INCREASE confidence, not destroy it.

3. AGGRESSIVE POSE AMBIGUITY MULTIPLIER
   Problem: (ambiguity + 0.2) * 4
   - Even low ambiguity of 0.1 becomes (0.1 + 0.2) * 4 = 1.2x penalty
   - Single high-ambiguity tags were being heavily discarded
   - No threshold check - even good tags got penalized

4. UNREALISTIC FINAL MULTIPLIERS
   - Could easily reach 20-50x multiplier for reasonable measurements
   - This essentially rejected many valid vision updates
   - Odometry drift accumulated without vision corrections


================================================================================
CHANGES MADE
================================================================================

New confidence calculation (lines 160-204) restructured into three components:

COMPONENT 1: DISTANCE FACTOR (lines 185-192)
Purpose: Reward close measurements, gently penalize far measurements

Behavior:
- Tags < 2.5 meters: 0.7x multiplier (30% CONFIDENCE BOOST)
  Justification: Close tags have lowest measurement error, highest reliability

- Tags 2.5-5 meters: 1.0x multiplier (neutral)
  Justification: Good sweet spot for most competition fields

- Tags > 5 meters: 1.0 + ((distance - 5.0) * 0.5) x multiplier
  Justification: Gradual penalty (0.5x per meter) instead of aggressive cliff
  Example: 6m tag = 1.5x, 7m tag = 2.0x (vs 30+ in original formula)

Why this is better:
- Rewards quality instead of penalizing it
- No cliff edge - smooth degradation with distance
- Still discourages over-reliance on far tags without killing them


COMPONENT 2: POSE AMBIGUITY FACTOR (lines 175-182)
Purpose: Only penalize single tags with genuine ambiguity issues

Behavior:
- Multiple tags (2+): 1.0x multiplier (no penalty)
  Justification: Multi-tag estimate is inherently less ambiguous

- Single tag with ambiguity ≤ 0.2: 1.0x multiplier (no penalty)
  Justification: Uses existing APRILTAG_AMBIGUITY_THRESHOLD constant

- Single tag with ambiguity > 0.2: 1.0 + (ambiguity * 2.0) x multiplier
  Justification: Gentler scaling (2.0x vs 4.0x in original)
  Example: ambiguity 0.5 = 1.0 + (0.5 * 2.0) = 2.0x penalty

Why this is better:
- Only penalizes when there's actual ambiguity
- Respects your existing threshold (no magic numbers)
- Gentler scaling - won't kill single-tag measurements
- Multi-tag estimates always trusted (as they should be)


COMPONENT 3: TAG COUNT BONUS (line 195)
Purpose: REWARD having multiple tags (opposite of original)

Behavior:
- 1 tag: 1.0 / (0.5 + 0.3) = 1.43x multiplier (slight penalty for being alone)
- 2 tags: 1.0 / (0.5 + 0.6) = 0.76x multiplier (22% confidence boost!)
- 3 tags: 1.0 / (0.5 + 0.9) = 0.56x multiplier (44% confidence boost!)
- 4 tags: 1.0 / (0.5 + 1.2) = 0.45x multiplier (55% confidence boost!)

Formula: 1.0 / (0.5 + (tagCount * 0.3))
- 0.5 = base denominator (prevents division singularities)
- 0.3 = scaling factor (tune this for more/less tag reward)

Why this is better:
- INVERTS the original logic (was penalizing multiple tags!)
- More tags = lower multiplier = BETTER confidence
- Physics-correct: more independent measurements = better estimate
- Encourages multi-tag solution (best case scenario)


FINAL SAFETY CAP (lines 198-201)
Purpose: Ensure measurements aren't completely discarded

Behavior:
- confidenceMultiplier = Math.max(1.0, factors)
- Guarantees minimum 1.0x multiplier applied
- Prevents measurements from being rejected outright

Why this is important:
- Even a bad measurement is better than no measurement (odometry drift)
- Allows pose estimator to decide if measurement is useful
- Graceful degradation instead of hard rejection

EXPECTED BEHAVIOR IMPROVEMENTS
================================================================================

Before:
- Single tags at various distances: heavily penalized
- Multiple tags: confidence DECREASED with each additional tag
- Distant tags (3-4m): often rejected completely

After:

================================================================================
TECHNICAL NOTES FOR DEVELOPERS
================================================================================

Code Structure:
- Lines 161-172: Calculate distances for all tags (unchanged from original concept)
- Lines 175-182: Ambiguity handling (refactored, much gentler)
- Lines 185-192: Distance factor (inverted logic from original)
- Lines 195: Tag count bonus (NEW - was destructive before)
- Lines 198-201: Final calculation with safety cap

Mathematical Properties:
- All factors are multiplicative (f1 * f2 * f3 * base)
- Each factor is 1.0 at "neutral" point
- Factors < 1.0 mean HIGHER confidence (WPILib convention)
- Factors > 1.0 mean LOWER confidence
- This matches SwerveDrivePoseEstimator expectations

Safety Properties:
- No division by zero possible (0.5 base in tag count bonus)
- No NaN/Infinity possible (Math.max guard)
- Graceful degradation (minimum 1.0x multiplier)
- Can be extended with additional factors (rotation rate, timestamp, etc.)

Integration Points:
- Called in ProcessVision4920() (lines 220, 238)
- Results passed to addVisionMeasurement() (line 246)
- Must be called after pose estimation (has access to EstimatedRobotPose)
- Standard deviation matrix interpretation:
  * [0] = X translation std dev (meters)
  * [1] = Y translation std dev (meters)
  * [2] = Rotation std dev (radians)


================================================================================
COMPARISON TABLE: OLD vs NEW
================================================================================

Scenario: 2 tags, closest at 2.0m, ambiguity 0.1

OLD FORMULA:
- Distance penalty: max(0, 2.0 - 2.5) * 7 = 0 → Math.max(1, 0 * 1.0) = 1.0x
- Ambiguity factor: 1.0 (multi-tag, no penalty)
- Tag presence: 1 + ((2 - 1) * 10) = 11.0
- Final: (1.0 * 1.0 * 1.0) / 11.0 = 0.091x multiplier
- Result: VERY HIGH CONFIDENCE (but undeserved penalty for having 2 tags!)

NEW FORMULA:
- Distance factor: 0.7 (reward for close tag)
- Ambiguity factor: 1.0 (multi-tag, no penalty)
- Tag count bonus: 1.0 / (0.5 + 0.6) = 0.76x
- Final: 0.7 * 1.0 * 0.76 = 0.53x multiplier
- Result: HIGH CONFIDENCE + LOWER MULTIPLIER (better physics!)

Why new is better:
- Old was accidentally high-confidence despite penalizing multiple tags
- New is intentionally high-confidence because multiple tags improve estimate
- New's lower multiplier (0.53) vs old's lower multiplier (0.091) is more realistic
- Old's factor of 11 for tag presence was extreme and wrong

================================================================================
QUESTIONS? NOTES FOR FUTURE REFERENCE
================================================================================

Q: Why not use a lookup table instead of formulas?
A: Formulas are more maintainable, scale across field sizes, adapt to camera changes

Q: Should we filter tags by ambiguity before this method?
A: No - this method handles that. But you could add an early-exit check if needed.

Q: What if we have 4-5 tags visible? Does it keep improving?
A: Yes, diminishing returns. But improvement caps around 0.3-0.4x multiplier with
   many tags (which is good - means highest confidence with most measurements)

Q: Can we use this with multiple cameras?
A: Yes - each camera calls confidenceCalculator independently, so each gets its
   own multiplier based on its targets. This is correct behavior.

Q: What happens if camera sees no tags?
A: EstimatedRobotPose is empty (caught earlier in getEstimatedGlobalPose), so
   this method isn't called. Falls back to odometry.

Q: Why 0.5 in tag count formula? Why 0.3?
A: 0.5 prevents division singularities and sets baseline.
   0.3 sets scaling - tune if needed per requirements.
   0.5 + (4 * 0.3) = 1.7, so even 4 tags only reach 0.59x multiplier (good cap).
